        Node graph editor — how it works
        
      

      

        
What you're looking at

        
Each chat preset (Coding, Research, Planning, …) is really a small agent
        tree: a lead plans the work, workers execute pieces of it in parallel, a
        reviewer checks the result, and a synthesis step writes the final answer.
        This canvas is that tree made visible and editable — the same tree the
        chat window runs when you use that preset.


        
Node types & wiring

        
    
          
  • Goal — the incoming request.
    • 
          
  • Memory — the same three-tier pool as the freeform canvas
          (tree / project / global). search pulls context into the lead
          before it runs; store writes the final answer back into that
          tier. Delete this node and save to opt the preset out entirely.
    • 
          
  • Model route — one candidate in the lead's real fallback
          chain: primary model, second choice, third, down to a guaranteed local-GPU
          fallback. This is the actual order auto-resolution tries models in — reorder
          by dragging port-to-port, or delete/add one, then Save.
    • 
          
  • Lead — plans the approach and delegates.
    • 
          
  • Worker — executes one focused piece of the task, in parallel with other workers.
    • 
          
  • Reviewer — checks worker output before synthesis.
    • 
          
  • Synthesis — a second lead pass that writes the user-facing answer.
    • 
          
  • Output — the final answer, streamed to the chat window.
    • 
        

        
Multi-wire fan-in/fan-out is supported: drag from a node's right-side port
        to another node's left-side port. Recursive mode allows feedback edges back
        into earlier nodes for iterative loops.


        
Loading & saving a preset

        
    
          
  1. Pick a preset from the dropdown (or leave it on "Active preset" — the
          one the chat window is currently using) and click Load preset tree.
    2. 
          
  2. Edit any node: pin an exact model, change required capabilities,
          cap cost, force a run location, or adjust the memory/route nodes.
    3. 
          
  3. Click Save. This writes your edits straight back into
          service_catalog.yaml — the same file the chat window's
          preset shortlist reads. There's no separate copy; editing the graph
          is editing the preset.
    4. 
        

        
Best-practice template loads a clean starting layout, useful for a
        new preset rather than editing a live one. From pipeline… and
        Export pipeline JSON convert to/from the separate
        aetherstack.pipeline.v1 "scripts" format.


        
Watching it run

        
When a real chat request runs against a preset — from this tab, the VS
        Code chat window, or anywhere else — the matching nodes light up gold while
        active and green once done, so you can see the actual lead → memory →
        workers → review → answer sequence happen instead of trusting it silently
        did the right thing. Runs started from this canvas's own Run
        workflow button now stream the same way — use Cancel run to
        stop one server-side, not just hide it in this tab.


        
Parallel node

        
Splits the incoming signal across several branches that run at the same
        time — set Parallel branches above 1 on a Worker node, or drop a
        dedicated Parallel node from the palette. Each branch
        prefers a different model where one is available (leave Model on
        "Auto-resolve" for real diversity), and their answers are combined into
        one [model]-labeled block for the next node — this is how you
        get several models' independent takes on the same input instead of just
        one.


        
Streaming

        
The Stream tokens live checkbox on agent nodes only applies to
        gateway-backed models (local Ollama or a cloud API key) — those already
        stream token-by-token today. Host-CLI-backed models (Grok/Claude/Codex CLI)
        cannot stream: the CLI bridge runs each as a subprocess and only gets its
        full output back once the process exits, so there is nothing to stream
        until that changes at the bridge level.


        
Node scripts (YAML if/then)

        
Agent nodes have an optional Script field: a small, sandboxed
        rules language evaluated right before that node runs — no arbitrary code
        execution, just a fixed set of safe conditions and actions.

        
rules:
  - if: contains(upstream, "security")
    then: { set_model: claude-opus-4, note: "Escalate — treat as security-sensitive." }
  - if: len(goal) < 20
    then: { skip: true }

        
Rules are checked top to bottom; the first one whose if is
        true wins (an empty/missing if always matches). Available in
        if: variables goal, upstream,
        model, label, role; functions
        contains(), not_contains(), matches()
        (regex), startswith(), endswith(),
        lower(), upper(), len(); operators
        and, or, not, ==,
        !=, <, >, in.
        then supports skip (don't run this node —
        anything depending only on its output is skipped too),
        set_model (force which model this node uses, overriding any
        parallel branches), and note (extra instruction appended to
        the prompt).

        
Two more examples:

        
# Only run this reviewer node when the worker flagged something risky
rules:
  - if: not contains(upstream, "risk")
    then: { skip: true }

# Route small/simple goals to a cheap fast model, everything else to the pinned one
rules:
  - if: len(goal) < 200 and not matches(goal, "(?i)security|migration|breaking")
    then: { set_model: local-default }

        
A broken script (bad YAML, an unknown variable/function) fails only that
        node — it's reported on the node's step as a script error, the rest of the
        run continues normally.
